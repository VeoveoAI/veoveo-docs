## Design change: the editor opens on its origin, not in a frame

The design had the `ui://n8n/editor` App frame `n8n.apps.{host}`. Measured at 09:24:35 in
the owner's Chrome, signed in at the app origin, from a page of `https://veoveo.bioma.ai`
(its `/.well-known/oauth-authorization-server`): a plain frame of
`https://n8n.apps.veoveo.bioma.ai/?frame=plain3` reached Hub with the session and was
forwarded, 200 in 21 ms; the same URL in a frame nested inside a frame sandboxed
`allow-scripts`, as an App's view is, reached Hub without it and got 401. A frame nested in
a view inherits the view's sandbox and opaque origin, so its requests are cross-site and
carry no session, and it has no storage. (A first attempt at 08:55:17 ran on a Chrome
error page, whose own origin made both frames cross-site; both got 401, and it is not
counted.) The change, in each owner's design and in the same commits as the code:

- SDK `10611ae`: a full web application's view opens its server's app origin with
  `ui/open-link` and frames nothing; `ui/open-link` admits a URL of the App's own
  server's app origin and an exact `ui://` resource of the caller's catalog; every other
  target fails.
- Hub `0ff0819`: the host page tells the view's host its server's app origin, and opens
  only that origin top-level for `ui/open-link`.
- n8n `924c973`: the App is a launcher; n8n keeps its `X-Frame-Options`.

Checklist I16's expected result changes from "frames" to "opens" accordingly.

## Unplanned fixes and incidents

- **The bridge's calls were refused by the factory's policy** (Bioma `e6d9909`). The first
  `resolve-time` run, execution 2 at 08:56:55, failed: OpenShell's proxy answered the
  server's `POST https://veoveo.bioma.ai/mcp/computer` with 403 `policy_denied`, "no L7
  endpoint path matched request". The factory base policy admitted Hub's metadata and
  token endpoints but not its MCP endpoint, which a server needs to call another server.
  The base policy now has a `hub_mcp` rule, `/mcp/*` with protocol MCP for the branch's
  binaries under `/sandbox/src`; applied with the `hub-claim` and `hub-control-plane`
  steps (4.0 s each).
- **A new sandbox minted a new encryption key** and n8n crash-looped from 09:09:13:
  "Deployment key 'signing.hmac' cannot be read with this instance encryption key".
  Revision 5 started in a new sandbox with an empty disk, where the server kept the key,
  so it minted another; the database still held n8n's data encrypted with the old one.
  Revision 5 did not change the image; the factory base policy had changed at 08:59:48,
  and a factory sandbox is created afresh when its base policy changes (inferred from the
  factory's rule, not traced in its log). The data being disposable, schema `n8n` was dropped (09:10:45,
  `DROP SCHEMA n8n CASCADE`, then `kernel.ensure_server('n8n')`), and n8n migrated afresh
  and listened at 09:11:11. The server's fix keeps the key with the data it encrypts, in
  the database; see below.
- **n8n's execution numbers restarted, and a run collided with an old Task's job.** After
  the reset, the run at 09:11:47 got n8n execution 2 again; core's Task tables still held
  the first execution 2's operation, and the dispatch failed on
  `task_operation_external_job` ("the Task could not finish its work"). The next run,
  execution 3, had no predecessor and passed. The server's fix names the n8n instance in
  the job; see below.
- **A poll during the restart failed in the client, not the run.** At 09:15:09 Hub answered
  the CLI's poll with JSON-RPC -32603: it could not discover the restarting instance's MCP
  ("connection closed before message completed"). The CLI then exited; the Task and the
  execution went on and completed. A caller polling through a restart gets that error and
  should poll again; the CLI does not.

## The server's fixes

n8n `d569ce5` and `523716a`, reviewed by the coordinator; the first adopted a key from the
disk, which was sent back as compatibility kept only for development data, and the
second makes the database the key's one source.

- **n8n's key lives with n8n's data.** The server's table `n8n.instance_key` (migration
  `0003`), one row per tenant, beside n8n's tables in schema `n8n`, is read at every
  start. With no row and no n8n tables, a key is generated and kept; with n8n's tables and
  no row, the start fails: "n8n's data in schema n8n cannot be read without its
  encryption key, which the database does not keep; reset n8n's tables". Before n8n
  starts, the server writes the key into n8n's own settings file, `.n8n/config`, keeping
  its other fields, since n8n refuses a file naming another key, as a disk that outlived a
  reset would hold. Every credential n8n holds is a provider's placeholder, so the key
  protects no real secret.
- **Nothing on the disk is needed to start.** The owner's password is new at every start,
  applied by n8n from the environment as a hash. On a disk without the server's API key,
  the server revokes its earlier keys under its label, which n8n holds once per label,
  and mints a new one.
- **A run's job names its n8n instance.** The key's row carries an instance ID, new with
  each row; a run's operation records its job as `{instance}:{execution}`, and the Veoveo
  Result and status-check events are named by the operation, not the execution. n8n's own
  `instanceId` was not used: n8n derives it from the encryption key.
- `401b33e` adds `workflows/undeclared-tool.json`, whose Veoveo Tool calls
  `time__list_sources`, a read-only Time tool outside the bridge table.

Component tests on the Mac: 59 of 59 (`cargo nextest`, stock n8n 2.46.0 under Docker for
the real-n8n tests), with fmt, clippy, deny, hack and `.sqlx` from an empty target. The
real-n8n test starts over an existing database on an empty disk with the kept key,
refuses the start when the row is deleted under n8n's tables, and replaces a stale
settings-file key; a runs test numbers executions from 1 again under a new instance and
completes both runs with distinct jobs.

## A lost wakeup in core's Tasks

The repository's `check` gate on the box at `401b33e` failed one test, rc 1 in 81 s, 58
of 59 passed: `an_n8n_started_again_over_a_reset_schema_never_meets_an_earlier_instances_runs`
left its Task `working`, "Waiting for n8n", last updated 0.18 s after its creation, until
the harness's deadline 47 s later. It had passed three times on the Mac.

Diagnosed by the coding agent, reviewed by the coordinator: a defect in core's
`veoveo-task` at the pinned `120306e`, present on core `main` then (`ef00952`), possible
in one server process. A worker parks its Task in one statement that locks the
operation's row, checks it is pending and sets the Task `waiting`. A delivery settles the
operation in one statement under the same row lock, and in the same statement queued the
Task if it was `waiting`. Under PostgreSQL's read committed, a statement that waited for a
row lock re-reads the locked row but reads every other row as it was when the statement
began: a delivery that began before the park committed settled the operation and found
the Task still running, so it queued nothing. The Task then waited on a settled operation
that no due check, deadline or recovery looks at again. The deadline pass had the same
shape. The park query's comment said the delivery "waits and then wakes the parked Task",
which read committed does not give.

Evidence: 30 iterations of the server's `runs` tests under 24 CPU hogs on 16 cores failed
3 times, twice in this test and once in `a_run_completes_…`; each left the operation
settled with the Result's outcome and the Task `waiting`, no owner, revision 3, the
delivery's statement starting 75 µs before to 2.59 ms after the park's. A core test,
`a_final_event_that_reads_before_the_park_commits_queues_the_parked_task`, forces that
order with row locks, waiting on `pg_stat_activity` rather than sleeping: at `120306e`
it fails (Task `Waiting`, expected `Queued`).

The fix, core `4ebcf89` on `main`: a delivery, by callback or by job, and the deadline
pass settle the operation in one statement and queue the parked Task in the same
transaction's next statement, `operation_wake.sql`, which begins after the lock was
granted and sees the park. A park that waits for a delivery's lock re-reads the
operation, finds it settled and does not park; the delivery holds the lock until it
commits, so no park falls between its two statements. Core's `platform/task/DESIGN.md`
states it. Core's `check` gate on the box: rc 0 in 177 s, 360 of 360. The deadline path
is fixed by the same reasoning without a test that forces its order; a cancellation
racing a park was not examined.

The coding agent reported two behaviours it did not resolve:

- A Veoveo Result that arrives before the dispatch records the job still completes the
  Task, but the operation then keeps no job.
- In the test harness, a restarted worker beside the routes' runtime makes two Task
  runtimes on one database; a run completed only by status checks after a restart once
  logged "the worker no longer owns the Task … changed concurrently" and stayed running.
  One server process has one runtime; whether core's status-check passes race across
  runtimes is not established.

## Boundaries

- I16's refusal without `n8n.editor` is Hub's component test, as in phase 1.
- The editor's page title reads "n8n[DEV]": the fork's image is built with n8n's
  development release channel. A follow-up for the fork's build.
- n8n's loopback listener, where the Veoveo nodes post, answers any process in the
  sandbox, so a node that makes HTTP requests, should a branch admit one, reaches it too;
  every call there needs a running run's token. Not probed; a follow-up.
- I14's restart was proven on `fa68d03` (core `120306e`); the runs after core's fix were
  probed on revision 8 without a restart mid-run.
- `veoveo-hub-sdk-cli` exits on a poll that fails while an instance restarts; it does not
  poll again.
- The factory base policy still admits every binary to any host on ports 80 and 443.
- Core's fix reaches only what is rebuilt on it. Media delivers provider events on core
  `d473011` and the SDK's hosted operations serve every server on an SDK before the bump;
  each keeps the lost wakeup until it takes a core at or after `4ebcf89`.
