### What PostgreSQL 19 changed

PostgreSQL 19 refuses to rewrite a table while a function with a SQL-standard body uses its row type, as a
knowledge read rule does: `cannot alter table "t" because function s.f(s.t) uses its row type`. Measured on
19.0 with such a function in place: `ADD COLUMN c int`, `ADD COLUMN e text CHECK (…)` and `DROP COLUMN` pass;
`ADD COLUMN … GENERATED ALWAYS AS (…) STORED` and `ALTER COLUMN … TYPE` are refused. Two places met it:

- **The SDK's knowledge test** retyped `item_id` and the vector column under `shop.item_readable`; each case now
  drops the rule, alters and creates it again in one transaction. `docs/SERVER_AUTHORING.md` says which changes
  are refused and that a collection's table is created with its knowledge columns.
- **Artifact's migration 2** added `knowledge_text` (stored, generated) to `artifact.artifact`, whose row
  `effective_level` (migration 1) reads, so a fresh database stopped at migration 2. The three knowledge
  columns moved into migration 1's `CREATE TABLE`; migration 2 keeps the indexes and the read rule. Old and new
  migrations were applied to a fresh 19.0 database on the box: the old stop at that error, the new pass.
  Artifact's `DESIGN.md` says where the columns are and why.

Rust 1.100.0's new lint flagged an unreachable call in the Hub: `error.to_string()` on the router's
`Infallible` error. The call now binds `let Ok(response) = …`.

## The database's upgrade

The deployed database was PostgreSQL 18.6: 10 databases, UTF8 `en_US.utf8` (libc), data checksums on, vector
and PostGIS in `veoveo`'s `_extensions`. `deploy.sh` counted every table's rows, scaled the StatefulSet to 0,
ran `upgrade.sh` in a pod of the upgrade image on the volume (initdb 19 with the old cluster's encoding,
locale and checksums, `pg_upgrade --link`, the old `postgresql.auto.conf` and `pg_hba.conf` carried over, the
new cluster moved to the old path and the old one removed), applied the installer's `postgres` step, ran the
`update_extensions.sql` pg_upgrade wrote, `vacuumdb --all --analyze-in-stages`, and counted again.

- **First attempt failed before any change.** PostgreSQL would not start the old cluster: `data directory
  "…/pgdata" has invalid permissions`. The pod's `fsGroup` leaves the directory at 2770; the image's entrypoint
  sets 0700 when the database starts, and the upgrade pod runs no entrypoint. `upgrade.sh` now sets 0700 on both
  directories. The StatefulSet waited at 0 in between.
- **Second attempt:** pg_upgrade 16 s, the postgres step 9 s, ready at 23:46:15, `update_extensions.sql`
  updated one extension, analyze 8 s. `veoveo` has postgis 3.7.0 and vector 0.8.7.
- **Rows:** the same before and after in every database, 324,053 in `veoveo` across 95 tables.
- **Downtime:** 23:44:19 to 23:46:15, 116 s including the failed attempt. The gateway logged "database
  unavailable" warnings in that window only. Hub, the gateway and Lore reconnected without restarts; USD's
  scene list answered as A and M and A saw 103 resources.

## Factory servers

`factory.sh` pushed the six mains into their Lore repositories' `main` as A at 00:12:15 to 00:12:24, n8n's
links `team-a` and `team-b` kept. Every build failed at its first step, `load metadata for
docker.io/library/rust:1.100.0-trixie@sha256:223cc32d…`: `failed to fetch anonymous token: Get
"https://auth.docker.io/token?…": dial tcp 198.18.0.6:443: connect: permission denied`. Each server kept serving
its earlier revision.

- **Cause.** A factory build runs `buildctl` in the Hub's sandbox, and `buildctl` fetches a registry's token
  itself; the Hub's policy reaches only BuildKit (`image_builder`, `buildkitd…:1234`). A base BuildKit already
  holds needs no token, so the bases it had built before resolved; `rust:1.100.0-trixie` was new to it. BuildKit's own pod resolved `auth.docker.io` to Cloudflare's
  addresses and fetched tokens (three requests); CoreDNS and the router answered the same in a minute's sampling at 00:21. That
  198.18.0.6 is the sandbox's own answer is inferred; the Hub sandbox's resolver was not observed. The
  2026-10-25 record's D2 had the same error on `docker/dockerfile`.
- **Retry.** Deleting the Lore pod (00:19:29, back in 6 s) ended the Hub's subscription, whose reconnect
  rechecks every branch; the seven builds ran again and failed the same way.
- **The base, from the box.** `warm.sh` built `FROM rust:1.100.0-trixie@sha256:223cc32d…` and `RUN true` on the
  cluster's BuildKit through a port-forward, with `moby/buildkit:v0.34.1`'s `buildctl`, which fetched the
  token from the box: 23 s. A second Lore pod deletion (00:24:52) retried the builds, and every server served
  its pushed revision by 00:41:42.
