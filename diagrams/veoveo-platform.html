Architecture

Veoveo gives each person a private Computer, a persistent sandbox where their coding agent works, and one entry point, the Hub, through which they use every service. Source code lives in Lore. When someone pushes a branch, the Hub builds it and runs it as a service. Every call to a service goes through the Hub, which checks who is calling and what they may do. A service that keeps records can be searched by meaning and words through one shared contract, and it searches only what the caller may read. People open files and USD scenes through the Hub, which frames them on a separate content domain that holds no session. All of this runs in OpenShell sandboxes on a K3s cluster, with PostgreSQL, object storage, an image registry and a GPU underneath. This view shows where each part runs in the reference installation.

Placement

  • Plain manifests on K3s: PostgreSQL (one StatefulSet), Lore, BuildKit, the registry, Vector and VictoriaLogs, and the tunnel connector. Helm releases: Cilium, SeaweedFS and the OpenShell gateway. Cilium enforces Kubernetes network policies; a sandbox’s egress also passes its OpenShell supervisor’s proxy.
  • OpenShell workspaces: installation (templates), vv-control (Hub), vv-services (console, Artifact, Media, media-provider, Embedding, embedding-runtime), vv-factory (branch instances, the USD server among them, and runners), and one per Computer owner.
  • The tunnel serves the host, the *.apps wildcard (sandbox.apps for App views, {slug}.apps for a server’s app origin) and *.veoveo-bioma.space, the content domain, past Cloudflare’s cache to Hub’s apps service.
  • The node’s RTX 4090: Embedding’s runtime holds a Kubernetes GPU claim, and a factory image opts in with no claim, as the USD server’s does.
  • On a Mac, development runs natively with Docker fixtures and a local Keycloak; there is no Mac cluster.

Read-only image mounts

  • The Lore CLI is mounted from the Lore image into Hub, Computers and factory sandboxes; the Hub CLI from the SDK CLI image into Computers.
  • Hub also mounts the file-viewer image and serves its files on the content domain; no other workload mounts it.
  • Read-only Kubernetes image volumes, pinned by digest and admitted only from listed repositories. Bioma’s component lock names each image once.
  • An upgrade builds one image and changes one value. Record 2026-10-25 ↗

Audiences

  • Hub application tokens, Lore tokens and OpenShell management tokens name different audiences, and each service accepts its own. Hub also accepts a Lore token for Lore’s listing, creation and deletion calls.
  • Hub administration gives no repository access; an administrator can publish assignments through the control-plane route.
  • Identities and trust boundaries ↗

Custody and placeholders

  • Computers, factory instances and runners hold placeholders for Lore, Hub and model credentials; the gateway stores the real values. Hub’s sandbox and the registered servers hold their own credentials.
  • A factory instance reads Lore as the branch’s latest pusher and cannot write: vv-factory-lore admits only the read RPCs of lore clone and lore sync --reset.
  • Strict binding, opt-in per profile, admits only a bound placeholder (I11). A runner gets only its team repository’s granted providers and, per call, the caller’s grant in its forwarded token.
  • A preview’s token names one browser session and one item, sits in the file’s origin and is checked on every request; a share link’s preview names the link and nobody. Hub issues the person’s Lore token for each read of a file, and it never leaves Hub for the browser or a server.
